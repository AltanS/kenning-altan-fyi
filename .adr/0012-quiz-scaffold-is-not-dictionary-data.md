# 0012 — The quiz scaffold is a shared pool, not dictionary data, and dedupes on a database row, not a pg-boss policy

- **Status:** Accepted
- **Date:** 2026-09-21
- **Deciders:** implementing agent (original design), Opus review pass (architecture review), operator (approved the required-changes list below)

**Provenance.** This document was authored end-to-end by the agent that built
M203, then reviewed by a separate Opus architecture pass before the operator
ever saw it. The operator did not review or approve the document as first
written; the operator's sign-off covers four specific required changes applied
afterward, and this text now reflects what actually shipped: the
scaffold-run re-claim fix (a `failed` or `budget` row is reopened rather than
a permanent lock), the enqueue-catch fix (a failed `orchestrator.start()`
releases the claim it just took), the `from !== to` guard on
`GET /api/quiz-deck`, and the `pnpm cli quiz scaffold-delete` escape hatch.

## Context

M203 adds a dynamic flashcard quiz built from a reader's favourites, their
search history and their answered `/explain` questions. A brand-new reader,
or one working a thin language pair, has too little of that material for a
quiz worth taking. The feature needs a fallback: LLM-written starter
vocabulary, generated once per language pair and shared by every reader of
that pair afterward, so the cost is paid at most once per pair rather than
once per thin reader.

Two existing patterns were candidates to build on: the dictionary-growing
translation job (`translate-headword.ts`, writes into
`headwords`/`senses`/`translations`) and the cache-and-answer jobs
(`translate-phrase.ts`, `explain-terms.ts`, each backed by a `stately`
pg-boss queue for per-request dedupe).

## Decision

**The scaffold is its own table, `quiz_scaffold_cards`, never dictionary
data.** A card is a flashcard-shaped fact, a word, a translation, an optional
note, with no sense id and no licence gate. It is generated by a workflow job
the same shape as `translate-headword.ts`'s (budget-reserved, one attempt,
terminal status on every exit), but writes nowhere near `headwords`,
`senses` or `translations`. This mirrors M195's decision that a phrase answer
is never dictionary data, for the same class of reason: forcing a flashcard
through the sense graph would buy nothing a quiz reads.

**Dedupe is a database row, not a `stately` pg-boss queue, and the row is
reclaimable.** `quiz_scaffold_runs` carries a composite primary key on
`(from_language_code, to_language_code)`. `claimScaffoldRun`
(`app/models/quiz.server.ts`) opens it with `INSERT ... ON CONFLICT ... DO
UPDATE ... WHERE status IN ('failed', 'budget')`; only the caller whose write
actually landed enqueues the job. A `pending` or `ok` row blocks every other
caller, the same as a plain `ON CONFLICT DO NOTHING` would, but a `failed` or
`budget` row (a budget refusal, a missing provider key, or a job that never
actually got queued) is reset back to `pending` for the next caller instead of
staying a dead end forever: this table is one mutable row per pair with no
append-only fallback, so a status that can never be reclaimed would be a
routine, everyday failure mode with no way back. The workflow template
(`scaffold-vocab.ts`) runs on the existing shared `default` queue and needs no
new queue, no `stately` policy, and no change to `app/services/workflows.server.ts`.
This is a deliberate step down from the machinery `translation`/`explain`/`enrichment`
each need: those jobs run per headword, many times a day, under real
concurrent load, and NEED a queue-level dedupe. The scaffold job runs at most
once per served language pair per genuine attempt (twelve pairs across four
languages), so a unique, reclaimable row is the correct amount of machinery.

**Favourites never cross the wire to the server.** They live in the device's
own store (ADR-0008/0011's plain-JSON sync blob), and the server has no query
that reads them as rows. `routes/quiz.tsx`'s `clientLoader` reads them
locally and sends only a COUNT to `/api/quiz-deck`, so the server can decide
whether a pair's organic material is thin enough to top up, without ever
learning which words those are.

**Quiz progress is session-only.** `app/lib/review/session.ts`'s queue,
shuffle and still-learning engine is reused unchanged (`quiz-session.tsx`
calls the same four functions `review-session.tsx` does). What is NOT reused
is `reviewState` persistence: a quiz card's id can name a `search_history`
row, an `explanation_asks` row or a shared `quiz_scaffold_cards` row, none of
which `reviewState` has a slot for, and "still learning" has no obvious
meaning yet for a word borrowed from a pool nobody chose to study. Persisting
verdicts for a mixed deck is a real product decision, deferred rather than
guessed at.

## Alternatives Considered

- **Write scaffold words into the dictionary via `translate-headword.ts`
  itself.** Rejected: it needs a real headword to translate senses of, and a
  scaffold backfill has no starting headword, it is asking the model to pick
  the words. Retrofitting an authoring mode onto that job would have coupled
  two features with different money-spend shapes and different retraction
  semantics.
- **Give the scaffold job its own `stately` queue, matching
  translation/explain/enrichment exactly.** Rejected for now: it is three
  extra edits to `workflows.server.ts` (the queue list, `createQueue`,
  `updateQueue`) to dedupe a job that structurally cannot fire more than
  twelve times in this installation's lifetime. The database row already
  makes a double-send impossible; a second, redundant guard would be
  ceremony.
- **Persist quiz verdicts to a new `quiz_progress` table.** Rejected for this
  milestone: it multiplies the scope (a fifth row shape, a merge story for a
  scaffold card a reader later favourites) for a feature whose first cut
  should prove the deck-assembly and scaffold-generation halves work at all.
  Tracked as out of scope in the milestone README, not silently dropped.

## Consequences

- A reader on a served pair nobody has quizzed on yet sees today's deck built
  from whatever organic material exists (possibly none); the scaffold pool
  fills in for the NEXT reader of that pair, not necessarily this one.
- A scaffold backfill that fails, whether the model call itself fails, the
  daily budget is used up, no provider key is configured, or
  `orchestrator.start()` throws right after the claim, leaves that pair's
  `quiz_scaffold_runs` row in `failed` or `budget`, not stuck: the next reader
  of that pair reclaims it through the same `claimScaffoldRun` call a
  first-ever request makes, and a fresh backfill is queued. The orchestrator
  being DOWN at the moment of the claim is the one case still handled
  differently, the claim is never taken in the first place (see
  `requestScaffoldIfNeeded`'s own guard), so there is nothing to reclaim: the
  next request simply tries again from scratch.
- An operator can also remove a pair's pool outright with
  `pnpm cli quiz scaffold-delete <from> <to>` (M203/04), which deletes both
  `quiz_scaffold_cards` and `quiz_scaffold_runs` for the pair. This is for a
  bad or wrong scaffold word, not for the stuck-row case above, which now
  self-heals.
- Every quiz session is independent: closing the tab loses "still learning"
  progress. Revisit if usage shows readers want the quiz to remember where
  they left off.
